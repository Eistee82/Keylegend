# Release 1.0.0 — design

Preparing Keylegend for publication on GitHub: a working installer, a release pipeline, and a
repository whose first commit is the release.

## Why this is not just packaging

`dotnet publish` does not carry `devices/`. `DeviceProfileLocator` walks up from
`AppContext.BaseDirectory` looking for that folder, finds nothing outside the repository, and the
application refuses to start. Measured in an isolated directory:

```
No device profile found. Pass one with --profile <path to device.json>.
```

Every installed copy would fail. That is fixed first, and a step in the release workflow makes
sure it stays fixed.

## Decisions

| Question | Choice | Reason |
|---|---|---|
| .NET runtime | Framework-dependent, installer checks for it | 2 MB against 167 MB measured for self-contained. The check turns a missing prerequisite into a link rather than a crash. |
| Artefacts | Inno Setup installer **and** portable ZIP | The installer is what most people want; the ZIP serves everyone who does not install utilities. |
| Install scope | Per user, `%LOCALAPPDATA%\Programs\Keylegend` | No elevation. It matches the program: autostart is a `HKCU` `Run` entry, settings live in `%APPDATA%`. A machine-wide install could not clean up other users' autostart entries on removal. |
| Console host | Ships with the installer | `--calibrate` is how a user corrects one of the thirty-one unverified profiles. Withholding it would ask for contributions and then remove the tool for making them. |
| History | One commit, tagged `v1.0.0` | Requested. It also drops `device.png` — a vendor product render — out of reach, which the licence audit flagged in commit `520b66b`. |

## Components

### 1. Shipping the device profiles

`Content` items in `Keylegend.App.csproj` and `Keylegend.Host.csproj` copy `devices/**/device.json`
into the output, preserving the folder structure the locator expects. Application profiles are
already embedded resources and need nothing.

The locator then finds the copy beside the binaries before it reaches the repository's own folder.
That is deterministic rather than dependent on where the binaries happen to sit, and a build
refreshes it.

### 2. The demonstration animation

Recorded from the running application. Not a reconstruction: the architecture document's central
claim is that the preview and the hardware are filled by the same code, and an illustration drawn
by other means would quietly stop being true.

Two parts:

- **What a key means** — base state, then Shift, AltGr, Windows, Ctrl, and Num Lock off. The
  layers switch, and the number pad recolours to navigation.
- **A profile per application** — Notepad, Windows Terminal and Explorer brought to the front in
  turn. The status line follows ("Profil: Notepad") and so do the key colours.

`tools/record-demo.ps1` drives it: UI Automation for the layer toggles, foreground switches for
the applications, `tools/screenshot.ps1` for each frame. That capture uses `PrintWindow`, so
Keylegend is photographed correctly while another application holds the foreground — which is
what makes part two possible at all.

`tools/build-demo.py` assembles the frames with Pillow, already a dependency of `make-icon.py`.
The frames are cropped to the header and the keyboard, which keeps the third-party donation
buttons out of the README image.

Written as an **animated PNG**, measured against the alternatives on the same ten frames:

| Format | Size | Average error | Worst pixel |
|---|---|---|---|
| GIF | 352 KB | 1.96 / 255 | 73 |
| WebP q95 | 312 KB | 1.60 | 55 |
| WebP lossless | 648 KB | exact | 0 |
| **APNG** | **1051 KB** | **exact** | **0** |

APNG costs the most and is still right. It reproduces the interface instead of approximating it
— 256 colours do not go far across anti-aliased text on dark gradients, and an illustration of a
program about colour ought to get the colour right. And it is a PNG: GitHub's documented image
types are PNG, GIF, JPEG and SVG, with WebP absent, so the smaller lossless option is not on
offer. A browser too old for APNG also degrades properly, showing the first frame as an ordinary
still image, where WebP would show nothing.

The script ships, following the precedent `make-icon.py` sets — the source is the script, the
binary is its product. Anyone changing the interface can regenerate the picture.

Output: `docs/images/keylegend.png`.

### 3. Version

`Directory.Build.props` at the repository root holds `Version`, `Company`, `Product` and
`Copyright` once. The release workflow passes `-p:Version` from the tag, so the tag and the file
version cannot disagree.

### 4. Installer

Inno Setup, `installer/keylegend.iss`:

- Per-user install, no elevation
- Start menu entry, optional desktop icon
- Closes a running instance before installing or removing
- Uninstall removes the `HKCU` `Run` value, and asks before deleting `%APPDATA%\Keylegend`
- Checks for the .NET 10 Desktop Runtime and offers the download page if it is absent

### 5. Workflows

`ci.yml` keeps building and testing every push and pull request.

`release.yml` runs on tags matching `v*`:

1. Test
2. Publish both executables, framework-dependent, with the version from the tag
3. Assemble a staging directory: binaries, `devices/`, `LICENSE`, `NOTICE.md`, `README.md`
4. **Smoke test** — run `keylegend-cli --dump-layout` in the staging directory and fail if no profile
   is found. This is the blocker above, turned into something that cannot silently return.
5. Build the installer, zip the portable copy
6. Publish a release with both artefacts and their SHA256 sums

### 6. Windows Package Manager

`packaging/winget` holds the four manifest files for `microsoft/winget-pkgs`, so the program can
be installed with `winget install Eistee82.Keylegend`.

Two details make this worth doing rather than merely possible. `InstallerType: inno` means winget
supplies the silent switches itself, so nothing has to be kept in step by hand. And the manifest
declares `Microsoft.DotNet.DesktopRuntime.10` as a dependency — which turns the one real drawback
of shipping framework-dependent into something the package manager handles: the runtime arrives
before the program does.

`tools/winget-manifest.ps1` fills the version and the installer hash in. It downloads the
published file rather than hashing a local build, because validation compares against what the
release actually serves. `.github/workflows/winget.yml` runs it manually, after publishing;
submitting the pull request stays a deliberate act, since it appears under the maintainer's name
in someone else's repository.

The `ProductCode` in the manifest was read back from a real installation rather than derived from
the AppId — it is what lets winget recognise an installed copy and offer upgrades.

### 7. Repository hygiene

Issue templates for bug reports and device profile contributions; a short `SECURITY.md` that
repeats the no-keyboard-hooks commitment. All eleven READMEs lose the "no packaged release yet"
banner and gain an installation section and the GIF.

## Testing

The 418 existing tests must keep passing. Beyond them, the packaging is checked by packaging it —
which is where every defect in this list came from, none of them visible to a build or a test:

| Found by | What it was |
|---|---|
| Publishing to an empty directory | `devices/` was not carried, so an installed copy had no keyboard to describe |
| Installing the result | The console tool and the application had the same file name under Windows' case rules; the release contained the tool and no interface |
| Driving the installed program | Layer buttons and settings checkboxes were wired to `Click`, which UI Automation does not raise — assistive technology moved the tick and changed nothing |
| Switching applications with a layer held | The header named one profile while the keyboard still showed another's layer |
| Uninstalling while it ran | The uninstaller left the directory behind, and a silent uninstall never closed the program at all |

So the checks live where they can catch a repeat:

- The release build refuses to package unless both executables are present and distinct, at least
  one device profile is there, and the published program can actually find one.
- CI runs that same packaging on every change rather than only at a tag.
- The winget manifests are checked against `Directory.Build.props`, so a version that disagrees
  with the build fails here rather than in someone else's repository.
- The installer itself is exercised by hand before a tag: install, start, switch autostart on,
  uninstall while running, and confirm what is left behind. An installer is not something to
  declare working without having run it.

## Not solved

Without a signing certificate, SmartScreen warns about an unknown publisher for both artefacts.
Normal for an open-source project, and stated in the release notes rather than left as a surprise.
