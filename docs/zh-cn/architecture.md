# 架构

## 核心想法

全部判断逻辑都是一次**纯计算**，不接触 Windows、网络或文件系统：

```
（键盘状态、已连接的键盘、应用程序配置、颜色设置）→ 每个按键的颜色
```

由此得出两点，而这两点正是整个设计取此形态的原因：

1. 屏幕上的预览和真实键盘由**同一段代码**填充。你在窗口里看到的，就是会亮起来的。
2. 这套逻辑无需连接键盘、也无需安装 Synapse 即可完整测试。

一切与外界打交道的东西，都待在这个内核外面薄薄的适配层里。

## 项目

| 项目 | 包含 | 可以依赖 |
|---|---|---|
| `Keylegend.Core` | 已连接的键盘、类别、快捷键集合、帧合成器、会话状态机 | 任何与平台无关的东西 |
| `Keylegend.Windows` | 键盘状态、字符解析、前台窗口 | Windows API |
| `Keylegend.Chroma` | Chroma SDK 的 REST 客户端、心跳 | 网络 |
| `Keylegend.Engine` | 读取键盘、合成一帧并发送出去的循环 | Core、Chroma、Windows |
| `Keylegend.App` | WPF 界面、通知区域图标、配置存储 | 以上全部 |

`Keylegend.Core` 绝不可以引用其他项目。若某项改动看起来非如此不可，那说明抽象放错了地方。

## 读取键盘状态

Keylegend **不**安装全局键盘钩子。这类钩子在功能上就是键盘记录器，位于输入链路之中，并且经常被
反作弊系统标记。

取而代之的是，程序每秒约六十次轮询关心的按键状态（按住的修饰键用 `GetAsyncKeyState`，锁定状态用
`GetKeyState`），只有当有东西改变时才合成新的一帧。任何击键都不会被拦截、转发、记录或保存。

### 左右修饰键

Windows 把 **AltGr 报告为 Ctrl 加右 Alt**，而在德语布局上 Ctrl + 左 Alt 产生的字符与 AltGr 相同。
二者按左右区分：

- **右 Alt** → AltGr 层，显示字符分配
- **Ctrl + 左 Alt** → `Ctrl+Alt` 快捷键集合

因此左右变体必须分开判断（`VK_LMENU`/`VK_RMENU` 等等）。

## 判定一个键意味着什么

Keylegend 不随身携带布局表，而是向 Windows 询问某个键在当前键盘状态下会产生什么字符
（`ToUnicodeEx`），再从得到的字符推出类别。

正因如此，Shift、Caps Lock 和 Num Lock 不需要任何特殊处理：同一个键只是返回 `A` 而不是 `a`，自己
就落入“大写”类别。也正因如此，任何键盘布局都无需改动即可工作。

### 接的是哪块键盘

去问 Razer Synapse，因为它已经知道。它会把每个已连接设备的描述写入
`…\Razer Chroma SDK\Devices\<guid>.json`：型号名称、以数字表示的物理布局、矩阵尺寸，
以及硬件实际拥有的每个键的扫描码。`SdkDeviceDescription` 读的就是它，键盘的任何信息都不靠推断。

键盘长什么样，来自同一份安装。Synapse 的界面是一个网页应用，它为设备加载的图纸留在缓存里：
带名字的键位矩形、含音量旋钮和多媒体条的外壳形状，以及键帽上印刷字符的轮廓。`SvgLayoutSource`
精确地找到所连型号与物理布局对应的那一张，而不是按形状去找，因为每张图纸旁都附有一个同时说明
两者的配置对象。

只取尺寸和轮廓；Razer 的配色与样式一概忽略，这些素材一点也没有复制进本仓库。

两者都没说的只有一件事：一个键属于灯光矩阵的哪个单元。那是 `StandardKeyMatrix`，协议自带的
`RZKEY` 表，在每个型号上都相同。

## 应用程序配置

一份配置把灯光规则绑定到一个程序上。随附的约有九十份，而它们背后的取舍值得说清楚，因为没有一个是显而易见的答案。

### 配置是数据，不是代码

与设备支持同一条规则：添加一份配置就是在 `profiles/` 下添加一个 JSON 文件，构建会按通配符把它收
进去。谁都不必碰 C# 就能教会 Keylegend 一个程序，这意味着一份配置可以由只熟悉该程序的人提交、审
阅和更正。如果支持一个新程序竟然需要代码，那说明格式错了。

### 嵌入程序集，而不是散落在磁盘上

应用程序配置被编译进程序集，而不是作为文件放在可执行文件旁边。有三条理由，每一条单独都够用。单文件发行版会把它
们一并带走，没有文件夹可丢。磁盘上没有东西会被误改，而正是这一点让“恢复随附版本”真正有意义——随
附版本必须在够不着的地方，才值得回退过去。而一份编译不过的配置会变成构建错误，而不是一个悄无声息
地没有任何配置的程序。

### 覆盖按小节进行

用户的修改从不以配置副本的形式保存。它保存为一条以配置 id 为键的覆盖，只包含被动过的小节。由此得
出两点：恢复才成为可能，而更新后的构建仍能改进某人已部分修改过的配置。id 承载着这一切，一经发布
就绝不可更改——改名会让别人的修改成为孤儿。

这一粒度在两个显而易见的替代方案面前站得住：

- **按字段**看着更整齐，却会产生没人配置过的状态。给 `W` 换个颜色，随后接受一次加入 `Q` 的更新，
  结果便是一种用户从未构建、也解释不了的混合体。
- **按配置**则是相反的失败。改一处名字，配置就被永久冻结；它再也见不到任何一次修正。

小节是这样一种粒度：在它之下，改动仍能用一句话说清——你编辑了高亮，那么高亮从此归你。

### 配置逐条叠加在通用集合之上

快捷键按修饰键组合编排，配置中的条目叠加在通用条目之上，而不是取而代之——逐条，而非逐层。Photoshop
知道 `Ctrl+J` 在 Photoshop 里是什么意思；它对 `Win+E` 一无所知，那是 Windows 在系统层面分配的，对
`Ctrl+C` 也一无所知，那在任何有文本光标的地方都成立。

逐层意味着一份为自己的命令点名 `Ctrl`
的配置会把整层一并带走，而代价就是剪贴板：复制、粘贴、剪切、撤销和全选会在浏览器里、聊天程序里、
终端里熄灭——而在这些程序里，人几乎只做打字和粘贴两件事。逐条叠加时，点名一个键只在该键上胜出，
别处分毫不动。把整层清空是有意做不到的。

不点名任何层的配置会原样返回通用目录，因此常见情形不占用内存。

### 快捷键和高亮都带标签

标签说明命令做什么——“复制图层”，而不是“Ctrl+J”。硬件从不显示它：LED 只承载颜色，别无其他，所以标
签在运行时不花任何代价。它在别处三次赚回本钱。程序内的预览可以显示它，测试可以发现条目之间的矛
盾，而在九十份配置的规模上，它是任何人得以核对某条是否正确的唯一途径。`"j": "编辑"` 无从对照；
`"j": "复制图层"` 则可以。

### 迁移格式 1 的设置文件

格式 1 的文件整份地保存配置，没有 id，也没有记录配置从何而来。一条覆盖需要一个 id
才能挂上去，而恢复需要知道存在一个可以退回去的随附版本——因此这样的文件说不出它的哪些条目是随附的。

于是它们全部变成用户配置。这保住了每一处有人做过的修改，代价是随附配置会与迁移来的副本并列，
直到两者之一被移除——这是正确的取舍，因为另一种读法会悄悄删掉别人的劳动。

### 迁移格式 2 的设置文件

格式 2 的文件列出所有颜色，连没人碰过的也一并列入，因此说不出哪些条目是决定、哪些只是被回写的默认值。
全部照办就会把调色板钉死：改进过的随附颜色便到不了任何曾经运行过本程序的人手上。

格式 3 只写与随附调色板不同之处，因此文件里的一个条目就意味着有人选了它。迁移较旧的文件只能去猜这个
区别，而所作的假定是：与该版本调色板相同的条目是默认值，其余都是选择。`PaletteBeforeFormat3`
把那份调色板存为冻结的副本，而不是去读当前的那份——那种比较会在调色板再次改变的那一刻失去意义，
而那正是需要它的时候。

代价是：有人当初刻意选了其中一个颜色，如今会丢掉。这个方向是对的——一个人重新选一次颜色，
胜过所有用户都守着一份没人选过的调色板。

## 与键盘对话

Chroma SDK 通过其本地 REST 接口寻址。颜色是 BGR 编码的整数；整块键盘写作一个 6 × 22 的矩阵。会话
必须用心跳维持。

在开发机上测得：创建会话需 60–125 毫秒，从正在运行的 Chroma Studio 效果接管后的第一帧约 500 毫秒，
此后每一帧约 2 毫秒。

### 每个回复都是 200，所以要看响应体

服务对**所有**请求都回以 HTTP 200，包括它已经丢弃的请求。矩阵尺寸错误的一帧会这样返回：

```json
{"error":"expecting a 2 dimensional array of 6 (rows) x 22 (columns) elements with integer values","result":87}
```

状态码仍是 200。因此只检查状态码，就会把键盘从未显示过的帧报告为成功：一次无声的失败，与灯光根本
没有变化毫无区别。

所以由响应体中的 `result` 决定：零表示成功，其他任何值都是拒绝。服务给出明文 `error` 的地方原样
保留，因为它比这里编造的任何措辞都更准确地指出真正的问题。用户能据以处理的代码会被翻译：

| 代码 | 含义 |
|---|---|
| 4309 | 在 Synapse 中该设备的 Chroma 已关闭 |
| 1152 | 另一个应用程序占用着会话 |
| 1167 | 没有连接 Chroma 设备 |
| 5 | 访问被拒绝 |
| 87 | 请求格式有误 |
| 50 | 请求不受支持 |

成功建立会话根本不带 `result`——它返回的是会话信息——因此没有 `result` 就算成功。

### 帧的发送频率

这看着像细节，其实不是；两个显而易见的答案都是错的。

**只在变化时发送**会让接管挨饿。普通击键并不改变键盘状态——只有修饰键和锁定键才改变——因此一次接管
恰好只产生一帧。Chroma 在仍在取得控制权时会丢弃帧，并且对这些帧报告成功，于是那唯一的一帧可能就此
消失，让键盘冻结在先前的效果上，直到用户碰巧按下某个修饰键。

**尽可能快地发送**则毁掉响应速度。帧会在接口内部排队，状态变化于是要排在已发送的一切之后——按下
Shift 明显要过一两秒才显示出来。

行之有效的做法是出于三种不同理由、以三种不同频率发送：

| 理由 | 频率 |
|---|---|
| 键盘状态发生了变化 | 立即——端到端实测 1 毫秒 |
| 接管后的三秒之内 | 每 120 毫秒一次，直到交接稳定下来 |
| 其他情况 | 每 750 毫秒一次，纯粹作为丢帧的保险 |

## 会话处理

| 状态 | 行为 |
|---|---|
| **空闲** | 无会话。灯光由 Chroma Studio 驱动。只有廉价的活动轮询在跑。 |
| **活动** | 会话已开，心跳运行中，每次状态变化产生一帧。 |
| **暂停** | 灯光被释放，直到恢复为止。 |

Keylegend 在首次按键时接管，并在可设置的空闲时间之后释放键盘，好让你自己的 Chroma Studio 效果回
来。因此那约 500 毫秒的唤醒代价只在真正停顿之后付出，绝不会在打字途中。

驱动键盘的只有一个 Keylegend 副本。两个副本会为同一台设备打开两个会话；服务只会把设备交给其中一个，
另一个什么也点不亮却依然报告成功——这看上去正像一个悄悄停止工作的程序。第二次启动做什么，取决于当时
正在运行的是什么。同一路径下的同一个程序，意味着有人在它位于通知区域时双击了图标：于是它的窗口会显
示出来，第二次启动则退出——什么都不会被结束，灯光也不会闪烁。其他任何情况——较旧的版本，或同一版本
但来自另一个文件夹——都会被取代：先请它退出，它交还自己的会话；只有在两秒内不作答时才会被直接结束。
